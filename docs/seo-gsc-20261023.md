# GSC-20261023 — canonical, robots.txt and sitemap

Owner split: Claude (code, tests, deploy of infovore) · Codex (Search Console
property, sitemap submission, Google-side verification). Submitting or reading
a sitemap in GSC is not the same as being indexed.

## Findings before the fix (2026-10-23 ~08:56 UTC)

- `/`, `/now`, `/stats` → 200, server-rendered, with `meta description`, but no
  `<link rel="canonical">`.
- `/robots.txt` and `/sitemap.xml` → 404 (GSC's robots report showed 404 on
  10/21). A 404 robots.txt means "allow all" to Google; it is not itself a host
  failure.
- `http://` → 308 to `https://infovore.skyhong.tw/` (Traefik
  `redirect-to-https@file`). `LEGACY_DOMAIN` equals `DOMAIN` in production, so
  no second host serves duplicate content.
- Host evidence (GSC "host had problems last week"): the shared Dokploy box has
  2 vCPU, swap fully used (4095/4095 MiB) and load ~4.5. infovore logged
  homepage reads of 7.9–26.4 s and trivial SQLite reads of 5–8 s at 09:00 UTC.
  The gateway already serves `/` from a last-good snapshot, but every other
  route is proxied behind a 3 s response-header deadline and returns 503 under
  that contention. robots.txt 5xx is what Google counts as a host availability
  failure (and it pauses crawling), so robots.txt must not depend on the
  backend. No timeout was raised; the underlying shared-host contention is
  outside this repo.

## Change

- `src/seo.ts`: dependency-free `publicBaseUrl`, `robotsTxt`, `sitemapXml`.
- `src/gateway.ts` / `src/server.ts`: `/robots.txt` served from gateway memory
  (GET/HEAD, 200, never proxied), so it answers even while the backend is
  starting, stalled or saturated.
- `src/output/pages.ts` `shell()`: optional `{ path, noindex }`. Stable public
  pages emit `<link rel="canonical">` + `og:url` on `PUBLIC_BASE_URL` (prod:
  `https://infovore.skyhong.tw`), independent of request host and query string.
  `/search` emits `noindex, follow` and no canonical.
- `src/index.ts` `/sitemap.xml`: registered before the card middleware, rebuilt
  at most hourly, lists only stable public HTML pages; a platform appears only
  while it has a last-good snapshot (restored from SQLite at boot, so upstream
  failures do not drop it or blank pages). No JSON, cards, feeds, search,
  `/status`, `/api*`, `/mcp` or ingest endpoints.
- robots.txt disallows `/api/` (JSON + authenticated ingest) and `/mcp`; the
  `/api` documentation page stays crawlable. Public/private boundaries are
  unchanged — robots.txt is not an access control; ingest stays bearer-auth.

- Google side (Codex): submit `https://infovore.skyhong.tw/sitemap.xml`,

## Round 2 — capacity, intermittent 503 and deploy cold start (2026-10-23 11:27–11:50 UTC)

### Bounded re-check before changing anything

- 11:27 UTC, anonymous, one request each: `/now` 200 0.31 s, `/stats` 200
  0.28 s, `/platforms/health` 200 0.56 s, `/healthz` `healthy` (all sources
  fresh, backend inFlight 0). Prod at `3a29ffe`, container healthy since 09:26,
  restarts 0. Host load ~3, IO wait 0 %, swap 3.9/4.0 GiB, no other builds.
- Last 3 h of `read-duration`: 25 reads ≥ 3 s, all in 09:34–09:35 (deploy
  warmup) and 10:17–10:25 (mostly the gateway's background homepage
  regeneration, which visitors do not wait for); none after 10:25.
- status.skyhong.tw history (1-min homepage checks, 10-22 11:30 → 10-23 11:30):
  23 down minutes, all in deploy windows (9 short runs 10-22 14:44–16:43 around
  the gateway rollouts, 6 min at the 10-23 09:27 deploy); none in steady state.
- Conclusion: the 09:33–09:35 intermittent `backend_deadline` was transient host
  contention and was **not** reproducible now. No change was made for it, and the
  3 s deadline was not raised. The deploy/restart gap **was** structural.

### Root cause of the deploy/restart gap

1. The container `HEALTHCHECK` probed `/healthz` (readiness + source freshness).
   Traefik's Docker provider routes only to `healthy` containers, so while the
   backend warmed (or any time it stalled > ~90 s, or all sources went stale)
   Traefik answered `404 page not found` for the whole host, although the gateway
   inside was alive and serving robots.txt, explicit 503s and the last-good
   homepage. Evidence: 09:27–09:32 in-container `wget /healthz` got the
   gateway's 503 while the edge returned Traefik's 404.
2. Startup whole-table Health aggregates ran on a cold page cache as 4 KiB random
   reads: `health_status` 79.8 s, `health_snapshot` 218.7 s,
   `health_activity_counts` 57.4 s. Measured on the same file with O_DIRECT:
   4 MiB sequential 215 MB/s vs 4 KiB 8.5 MB/s even on an idle disk.

### Fix (commit `154e84f`)

- Gateway `GET /livez` = process liveness; Dockerfile `HEALTHCHECK` now probes it
  with `--start-interval=2s`. `/healthz` is unchanged (readiness/freshness for
  monitors; status.skyhong.tw checks the homepage over HTTP, not Docker health).
  Ingest answers `/livez` with its existing configuration health.
- `src/prewarm.ts`: before `index.js` opens SQLite, the app child reads the DB
  file and WAL once sequentially (4 MiB chunks, 60 s cap raced by a timer because
  a stalled read cannot be cancelled; advisory only). No query, projection,
  visibility, last-good, freshness, ingest-auth, canonical/sitemap or robots
  behaviour changed.
- `npm run check`: 170/170 (new `tests/liveness.test.ts`: healthcheck targets
  `/livez`; gateway live while backend starting and `/healthz` still 503;
  ingest `/livez`; prewarm reads, tolerates ENOENT, stops at its deadline on a
  blocked FIFO).

### Deploy and acceptance (same revision `154e84f`)

- Same compose flow (build while the old container served, then recreate; no
  second stack). Previous image tagged `infovore:rollback-3a29ffe`. New image
  `sha256:1d7744226d56…`, healthcheck `{"Test":[…"/livez"…],"StartInterval":2s}`.
- Edge probe every 3 s (robots / home / healthz), recreate at 11:43:46:
  11:43:50 Traefik 404 → **11:43:54 robots 200**, home 503, healthz 503 (explicit
  gateway 503s) → 11:44:52 healthz 200 → **11:45:07 home 200**. Edge 404 window
  ≤ 8 s (was ~6.5 min); homepage back after 81 s (was ~6.5 min).
- Startup reads after `[prewarm] read 765 MiB in 7353 ms`: `health_status`
  10.0 s (was 79.8), `health_snapshot` 31.1 s (218.7), `health_activity_counts`
  14.8 s (57.4), `activities_list` 1.8 s (6.4). The remainder is CPU for
  whole-table `json_extract`, not cold IO.
- Rollback: `docker tag infovore:rollback-3a29ffe infovore:latest`, check out
  `3a29ffe`, `docker compose -f docker-compose.yml -f docker-compose.traefik.yml up -d --no-build`.

### Remaining risk (not fixed, by design)

- During the ~80 s warmup, `/healthz` can flap 200/503 and upstream refreshes
  started in that window time out once (retried after 2 min on last-good data).
  Persisting Health aggregates across restarts would shorten it further; no
  evidence yet that it is needed now that the edge keeps routing.
- Shared-host contention can still slow proxied pages past the 3 s deadline
  (explicit 503, never an edge 404 now). Capacity changes belong to the host
  owner; other projects' services were not touched.
